The GitHub release assets are available at https://github.com/villagesql/villagesql-server/releases.
The Docker Hub release artifacts are available at https://hub.docker.com/r/villagesql/server.

## What's New

### Extensions

- **Per-session system variables (preview)** — Extensions can declare per-session system variables through the `vsql::session_var` capability, the session-scoped sibling of `vsql::sys_var`. Every connection holds its own value, settable with `SET SESSION`, and the declared default is the global default. `INT` and `STR` variables are supported. A VDF reads the calling session's value through `int_var()`, `get_session_int()` or `get_session_str()`. Like every preview capability, it requires `vsql_allow_preview_extensions=ON`. The server side backports the component session-variable service and its reader service from upstream MySQL. (`699a0bbf286`, #1059; `494c58d1770`, #1057; `9fd09db4f34`, #1115; `17df24684f5`, #1209)
- **`on_init` and `on_deinit` run with capabilities populated** — `on_init` ran inside `vef_register`, before the server populated the extension's capabilities, so the hook could not read its own system variables: the storage pointer was still null and `get()` had no vtable. `on_deinit` had the matching problem, running at `dlclose` after capabilities were already depopulated. Both hooks now live in the registration struct and the server calls them, `on_init` once populate succeeds and `on_deinit` before depopulate. At startup they are deferred until persisted values have been applied. The two must be declared together: the builder rejects a half pair at compile time, and the server checks again at load, which catches a protocol 4 extension that the SDK did not build. A rejected load runs neither hook, and at startup it fails extension loading rather than skipping the extension. An extension built against protocol 3 or earlier carries no such fields and is unaffected. (`c857bdf32ce`, #1216)
- **`bind_and_check_types`, defined but not yet called** — The contract for a VDF hook that resolves its own type parameters is now in the SDK, ahead of the server work that will invoke it. It is for a function whose return-type parameters the built-in disambiguation rules cannot work out. The hook sees each argument's kind, its resolved parameters, and its literal text when the argument is a string constant; it answers with the return type's parameters, optionally each argument's, or an error. The C ABI adds `vef_bind_types_args_t`, `vef_bind_types_result_t` and `vef_bind_types_func_t`, and appends `bind_and_check_types` to `vef_func_desc_t`. The typed C++ form is `void my_hook(vsql::BindArgs args, vsql::BindResult out)`, registered with `.bind_and_check_types<&my_hook>()`, which static-asserts the signature; `BindResult` answers with `set_return(params)`, `set_arg(i, params)` or `error(msg)`. Nothing in the server calls the hook yet, so registering one has no effect on this release. (`999445f7302`, #1200; `cf058c6f9f8`, #1201)
- **Authentication methods choose how roles are reconciled (preview)** — The `vsql::preview::auth` capability replaces the `auto_grant` callback with `roles_mode`, which returns one of three values and is queried live on every login. `VEF_AUTH_ROLES_ACTIVATE`, the default, only activates roles the account already holds, so a claimed role that is not granted is skipped and the DBA keeps ownership of grants. `VEF_AUTH_ROLES_GRANT` also grants a staged role the account lacks. `VEF_AUTH_ROLES_SYNC` makes the staged set authoritative: it grants the missing roles and revokes every granted role that is not staged, for deployments where the identity provider is the only source of truth. An extension using `auto_grant` needs updating before it compiles again. (`6f668d151dd`, #1188)
- **Enum system variables** — The `vsql::sys_var` capability gains `make_enum()`. The value is one of a fixed, ordered list of names, stored as its zero-based index; the server validates at `SET` time and rejects a name that is not on the list, unlike a free-form string variable. (`26e94477f9f`, #1179)
- **Client information in statement events** — The `vsql::preview::statement_event` capability now reports the client's connection attributes: the client process id (`_pid`), the connector library (`_client_name`) and the application name (`program_name`). Each is `NULL` when the client did not send it. (`89e0e43f38e`, #1178)
- **Persisted extension variables apply at `INSTALL`** — A persisted value for an extension variable with an `on_change` callback was applied before the variable was recorded in the registry, so the update handler found nothing to write. An `INT` silently kept its default. A string variable was left pointing at memory MySQL had already freed, and `UNINSTALL EXTENSION` freed it again: an assert on debug builds, heap corruption on release builds. The typed write is now unconditional, and `on_change` fires for a persisted value applied at `INSTALL`. A `SET` that races an `UNINSTALL EXTENSION` no longer crashes. (`361196a45d1`, #1129)
- **`STRING` results carry their declared character set** — A VDF registered with `.returns(STRING)` declared `utf8mb4_bin` in its metadata but returned a binary-charset string at runtime. The JSON functions decide text versus binary from the runtime charset, so `JSON_OBJECT('ts', UUID_TIMESTAMP(u))` produced `{"ts": "base64:type15:..."}` unless the caller wrapped the value in `CONVERT(... USING utf8mb4)`. The runtime charset now matches the declared one. (`e6c298d8925`, #1054)
- **VEB installs are synced to disk** — `INSTALL EXTENSION` now `fsync()`s the files and directories it writes from a VEB. (`ea958becc70`, #1145)
- **SDK version comes from the server build** — The SDK version is generated from the server build version and no longer carries the codebase name. (`323a6ec9265`, #1096; `f892efbb034`, #1064)
- **SDK documentation** — The useful comments from the v1-style SDK moved to the `vsql` SDK and the v1 comments were removed, so nobody picks up the old API by accident. The C++ SDK comments stop describing the typed API as wrappers. The header comments on intrinsic defaults said a computed default took precedence over a string default and gave the default VDF an `INT` argument. Declaring both is rejected at registration and the VDF takes no arguments, and the comments now say so. (`3d0d1484935`, #901; `a5d49e67f99`, #898; `8682dfe1528`, #1170)

### Custom Types

- **Type parameters are validated** — For the `TYPE`, `TYPE(N)` and `TYPE('k=v,...')` forms, the server now rejects a duplicate parameter name, a nameless parameter and a parameter with no value before the extension's `resolve_params` callback runs. After the callback returns, a rewrite that dropped a parameter is rejected. Adding parameters and changing values stays legal. (`c17123af77d`, #915)
- **Custom type DDL is refused under `LOCK TABLES`** — A custom type operation writes to the VillageSQL system tables, which are not in the user's locked-tables list, so opening them failed deep inside `open_tables()` with an `ER_TABLE_NOT_LOCKED` naming the internal `custom_columns` table. The statement is now rejected up front with `ERROR HY000: Custom type table operations are not supported under LOCK TABLES.`, and the table is left unchanged. `ALTER TABLE` on columns of built-in types is unaffected. The rollback guard was also moved ahead of `process_alter`, so a failure inside it unwinds the metadata it had already staged. (`902649b7d34`, #1192)
- **A temporary table no longer inherits a base table's custom type** — A temporary table shadowing a base table of the same name took the base table's custom type for any column sharing a name, because the lookup fell through to the victionary, which is keyed on database, table and column. The session map is now the only source for a user temporary table's columns. (`76d4c704720`, #1191)
- **`DROP DATABASE` removes stored program parameter metadata** — Dropping a database bypassed the per-routine `DROP` path that cleans up `villagesql.custom_sp_params`. Rows for procedures and functions with custom-type parameters in the dropped database were left behind. They are now deleted with the database. (`738b26db28d`, #1121)

### Clone

- **Clone validates VillageSQL extensions before transferring data** — A remote `CLONE` used to succeed, overwrite the recipient, and only then fail at restart, because the donor's `villagesql.extensions` rows arrive as InnoDB data while the `.veb` bundles live outside the data directory and are not cloned. During the `COM_INIT` handshake, and before any data moves, the recipient now checks that every extension installed on the donor is present in its own `veb_dir` with a matching version and `.veb` sha256, the same bar the server applies at startup. A mismatch aborts the clone with a VillageSQL error naming the extension, for example `ERROR HY000: VillageSQL: VEB file for extension 'vsql_complex' not found`. The clone plugin reaches VillageSQL only through a new `vsql_clone_protocol` component service, mirroring how it already validates plugins, character sets and configuration. VillageSQL negotiates its own protocol version in reserved high bits of the clone version word, so a vanilla donor degrades gracefully and upstream versioning does not collide. (`8587d977342`, #1122)

### Information Schema

- **`sys` view column nullability matches upstream** — Four `sys` views that read the VillageSQL overrides of `INFORMATION_SCHEMA.COLUMNS` and `INFORMATION_SCHEMA.STATISTICS` recorded columns as `NOT NULL` where upstream MySQL records them as nullable: `schema_object_overview`, `x$schema_flattened_keys`, `schema_auto_increment_columns` and `schema_redundant_indexes`. Upstream creates its views in strict mode, where a `COLLATE` or `CONCAT` column stays nullable; the overrides are created with `sql_mode = 0`, where it does not. The server now replays the four views' DDL at startup. The `schema_auto_increment_columns` drift dates from the `COLUMNS` override in 0.0.1. (`f595f2e2251`, #1110)

### Custom Indexes (in development)

Custom index DDL is still refused by default, with `Extended Index feature not yet implemented`. Setting `vsql_allow_preview_extensions=ON` accepts it, and the MTR suites reach it through a debug-only switch. The metadata column widenings apply on any build, and the SDK signature change breaks an existing custom index extension at compile time. Everything else here needs the preview flag or the debug switch.

- **Metadata and DDL surfaces** — `SHOW CREATE TABLE` renders a custom index as valid DDL, including its type, per-key-part profile and `WITH` parameters. `INFORMATION_SCHEMA.STATISTICS.INDEX_TYPE` and `SHOW INDEX` report the extension's own index type name instead of `BTREE`; `INDEX_TYPE` widens from `varchar(11) utf8mb3_bin` to `varchar(64) utf8mb4_bin`. An externally-stored custom column wider than the key-length limit can now be indexed; the extension is responsible for its own key-size limits. InnoDB implements `col_ref_to_data` and `col_data_to_ref` for extension-managed column storage, with a new `key_pos` parameter; this changes the SDK API, so existing custom index extensions need updating before they compile again. As a consequence of the `INDEX_TYPE` widening, `sys.schema_object_overview.object_type` widens from `varchar(19)` to `varchar(72)`. (`d9eefc101ce`, #1067; `a7929efbb62`, #1076; `93813b3e96e`, #1035; `bd46c3a559e`, #1015; `6f416c97ce8`, #1111)
- **Nearest-neighbor scan** — A KNN-capable custom index can serve a query that orders by a distance function over the indexed column and takes a `LIMIT`, so the rows come back nearest first and no filesort runs. A shared recognition core decides whether the `ORDER BY` term matches the index's selected profile and builds a per-query scan spec; execution drives the extension's begin, next and end callbacks and fetches each hit's row by row id. The index is not MVCC-filtered, so a hit on a row the transaction's read view cannot see is skipped and the scan moves to the next candidate. Both optimizers use it: the hypergraph optimizer describes the path as `Custom index distance scan on <index>`, and the classic optimizer reports the new join type `index_distance`. InnoDB supplies the row-id lookup and the handler holds the scan. (`131989f41e6`, #1214; `a436a42ee7f`, #1210; `d58d8395752`, #1212; `553f55f989f`, #1213)
- **DML the index cannot maintain is refused with a clear message** — On a table carrying a custom index, a `DELETE`, an `UPDATE` that changes an indexed column or the primary key, and a `CREATE INDEX ... USING EXTENDED` on a table that already holds rows are not supported yet. Each is rejected before anything is modified, with the reason returned to the client: `DELETE on a table with a custom index (USING EXTENDED) is not supported yet.`, `UPDATE that changes an indexed column on a table with a custom index (USING EXTENDED) is not supported yet.`, and `CREATE INDEX ... USING EXTENDED on a non-empty table is not supported yet; create the index before loading data.` An `UPDATE` that touches no indexed column still proceeds. (`0cbff6a6848`, #1223)
- **An extension's own index error reaches the client** — When an extension's create or drop hook for a custom index fails, its message is returned as the statement's error rather than only reaching the server error log. (`3df9b2737ea`, #1220)

### Stability

- **Server starts on big-endian platforms** — On a big-endian host the server failed its first start with `Failed to install VillageSQL schema on first run`. The schema id read back from `mysql.schemata` arrives in host byte order and was being converted with a little-endian helper. Verified on `linux/s390x`. (`33efda8d2f9`, #1049)
- **Valgrind memcheck** — A workflow runs the full VillageSQL MTR suite, the unit tests and the bundled extensions under Valgrind memcheck, started after every nightly build by the nightly dispatch and available on demand. Extensions are built with `-DVSQL_VALGRIND=ON` under it, so they can compile conditionally. The restart tests shut the server down through MTR's standard mechanism, so its timeouts scale with the slowdown memcheck adds. `Docs/WRITING_MTR_TESTS.md` writes the convention down. Two indexing defects came out of it: an uninitialized pointer read in `Custom_index::add_profile`, and an uninitialized `dtype_t::extended_storage`. (`cbe719062ed`, #1157; `3cc9f680ca7`, #1160; `c6c8f3faacd`, #1165; `b14c1e68215`, #1169; `76e9c89557e`, #1173; `95ed8cc3bf8`, #1181; `c122288a82e`, #1205)
- **ThreadSanitizer** — A ThreadSanitizer workflow builds with `-DWITH_TSAN=1` and runs the unit tests, the VillageSQL MTR suite and every bundled extension rebuilt with `-fsanitize=thread`. The nightly dispatch starts a run after every nightly build. Upstream MySQL is not TSan-clean, so `mysql-test/tsan.supp` mutes `race:innobase` and `race:perfschema` wholesale, a handful of named upstream server races and lock-order cycles, and the error log's timestamp counter. Nothing under `villagesql/` or in the extensions is suppressed, which is the coverage the workflow exists for. `llvm-symbolizer` is installed for readable stack traces, with a workaround for symbolizing plugin `.so` files. Two findings were fixed rather than suppressed: the clone protocol version is now atomic, and `register_variable()` no longer holds `LOCK_plugin` across `set_persisted_options()`, which also removes one lock-order arc TSan reported as a cycle. (`96ca4d8fb1a`, #1185; `bf1302d7793`, #1226; `90a540c25e6`, #1219; `1e1188bf18f`, #1217; `3688a86c84b`, #1195; `606d247f0bb`, #1193)
- **Test coverage** — Gcov-guided additions to the MTR suites cover the full write-side storage ABI with two column-store columns in one table, the `EXTENSION` MDL wait event, custom-type stored-procedure parameters through a pending upgrade, `FULLTEXT` on tables with custom-type columns, and rollback of extended-storage values. New unit tests cover the deferred extension version update stored in `villagesql.extensions.pending_action`, semver edge cases, and `TypeContext`. An extension downgrade test exercises `ALTER EXTENSION` to an earlier version. A test covers the locking assumptions behind a suspected crash, an `UNINSTALL EXTENSION` racing a `SET GLOBAL` on an extension variable. (`d665614d687`, #984; `54ce39b7620`, #957; `e6f17e8c41f`, #1153; `bb95002a73a`, #1137; `10a099c37bd`, #1123)
- **A view over a dropped custom-type column no longer crashes the server** — `SHOW CREATE VIEW` on a view whose select list calls a VDF over a column that `ALTER TABLE` has since dropped dereferenced a null function descriptor and killed the server. The statement now prints the stored definition and raises warning 1356, `View 'test.v1' references invalid table(s) or column(s) or function(s) or definer/invoker of view lack rights to use them`, the way MySQL reports any other broken view. (`0701227ff6f`, #1228, #1199)
- **`connection_not_alive` is stable under parallel runs** — The test checked that a cancelled connection was gone while it was still blocked on a lock another session held, so the assertion raced that session's unlock. An aborted session blocked on a lock wait is reaped when its statement unblocks, not when the client goes away. On an idle machine the macro's own delay usually hid the gap; under parallel runs it did not. The liveness check now runs after the lock is released. (`c54c1640202`, #1171)

### Build & Compatibility

- **Native RPM and DEB packaging** — Packaging sources and build scripts for native packages land in `packaging/villagesql-rpm/` and `packaging/villagesql-deb/`, driven by `villagesql/bld_tools/build_rpm.sh` and `build_deb.sh`. They are kept in new directories rather than modifying the upstream-owned `packaging/rpm-oel` and `packaging/deb-in`, so the MySQL rebase surface is unchanged. The packages take over an existing MySQL install rather than sitting beside one: same binary names, data directory, systemd unit name and port. Epoch 1 is required, because VillageSQL versions as 0.0.x while MySQL is at 8.4.x and the `Obsoletes` and `Replaces` would otherwise never compare as an upgrade. Pre-releases use `~dev` rather than `-dev`, since both dpkg and rpm sort `~` below the plain version. Neither choice can be revisited once a package ships. NDB and Router are off, as upstream ships both separately. Build dependencies resolve on EL8, EL9, EL10, Ubuntu 24.04, Ubuntu 26.04, Debian 12 and Debian 13; the takeover was tested in clean containers against MySQL 8.4.11 on EL9 and MySQL 8.0.46 on Ubuntu 24.04. SELinux policy for loading `.veb` bundles from `/usr/lib64/mysql/veb` on an enforcing host is not covered yet. No workflow builds or publishes these packages, so the release artifacts are unchanged for now. (`ea623810efb`, #931)
- **Ubuntu 26.04 builds** — The CI runners moved to Ubuntu 26.04, and the newer compiler surfaced new diagnostics. One more libarchive warning is allowlisted. A latent bug is fixed: `TypeParameters::from_raw()` lower-cased an empty parameter name or value, which is undefined behavior. An upstream MySQL bug in the Group Replication plugin's call to `inet_ntop()`, which passed the size of the address struct where the size of the destination buffer belongs, is corrected. A LeakSanitizer suppression covers the Rust coreutils that newer Ubuntu ships. (`cf3499be13c`, #1097; `9057fe31137`, #1107; `9d85e0a5119`, #1108)
- **Client banners name VillageSQL** — Every binary that prints the shared copyright notice now prints a `Copyright (c) <year> VillageSQL Contributors` line above the Oracle line, `mysqld`, `mysql`, `mysqladmin`, `mysqldump` and `mysqlbinlog` among them. A test covers a spread of those call sites, because the notice comes from an Oracle-owned macro that a future upstream merge could silently take back. (`f14e0a5d6eb`, #1198)
- **Docker image streams the bootstrap server's log** — The entrypoint printed the temporary server's log once, when the server reported ready, so anything written after that was lost if the script exited early. The log is now tailed to stderr continuously. (`06ae8da633c`, #1152)
- **Docker dev container runs as non-root** — The development container creates a user with the host's uid, gid, user name and group name. Files written back to the host keep the host user as owner, and MTR tests that start `mysqld` themselves no longer fail for lack of `--user=root`. The container also adds a data directory volume, drops the hardcoded resource limits, and grants the user password-less `sudo`. Rebuild the image with `docker/dev/build.sh` on the machine that will run it. (`85f12e9eb14`, #1126)
- **Docker Hub manifests for multiple codebases** — The publish workflows push and tag multi-platform manifests per codebase, so each codebase has its own `latest` (`mysql-8.4_latest`, `mysql-9.7_latest`, `percona-8.4_latest`) and Docker Hub selects the right platform image. Release images are tagged per codebase, for example `mysql-8.4_0.0.7`. The `linux/amd64` image builds moved from GitHub's `ubuntu-latest` to the VillageSQL self-hosted runner pool. (`6f1c4988e37`, #1065; `4dbfcca7c5a`, #1174)
- **Release automation** — The acceptance test for a codebase release branch and the generation of release artifacts run as dispatched workflows. Scripts create the draft GitHub release from the tag and the release notes, and finalize the release notes header. A script rewrites the three version numbers in `VSQL_VERSION` along with the test results that embed the version string, and commits only those files. `create-release.yml` lands the two release commits on a frozen branch in one push, tags the release, drafts its GitHub release and hands the publish tag to the codebase release dispatch. (`2b985c04f13`, #1083; `2b99129bcfc`, #1125; `5e8ab844da8`, #1082; `b4344ce7dda`, #1086; `3b47edc9de8`, #1091; `91b250d46eb`, #1093; `350b0e0cdf7`, #1095; `38495b40f4f`, #1175)
- **Nightly and full test suite CI** — The sanitizer and extension-compat workflows are driven by the nightly dispatch rather than an unparameterized trigger. The Full Test Suite can choose its runner and gains a nightly macOS run. Test reporting includes retry details and preserves results when MTR reruns unstable tests to success. The slow `max_parts` tests and three other long-running tests get testcase timeouts sized to GitHub runner speed. `lock_order.cycle`, which needs a server built with `-DWITH_LOCK_ORDER=ON`, is disabled. (`39d5d8b8955`, #1071; `a7790b71ef2`, #1072; `6442c74867e`, #1038; `6d147a1b021`, #1114; `2deed4a37f8`, #1146; `2c7bb6fa3a6`, #1130; `2a1a1344475`, #1134; `4d7152888a8`, #1163; `7f8af9db1c8`, #1164; `2eb58eefbb6`, #1167; `41181a73177`, #1166)
- **Pull request checks** — The separate label, auto-merge and prow-command workflows are replaced by one workflow built on the `cncf/prow-github-actions` project, which handles the slash commands, the `needs-*` labels, OWNERS-based review and `lgtm` merging. The PR title check allows 63 characters, up from 41, so a squash-merged title stays under GitHub's 72-character limit. The `villint` tests no longer depend on a global git config. (`9998b5e1dc4`, #1207; `f436c0f953b`, #1080; `aba58cfba3f`, #1176)
- **README and policy** — The README test steps pass `--nounit-tests`, since the upstream unit tests have a couple of known failures, and its roadmap section points at the published roadmap instead of carrying its own list. The build instructions in the README, the Docker guide and `AGENTS.md` drop `-DWITH_SSL=system`, which is already the default, and the macOS line resolves OpenSSL through `brew --prefix` rather than a hardcoded path. The bundled-extension build scripts document their inputs. The AI policy in the contributing guide now covers issues as well as pull requests and states that AI code review assistants such as Copilot are not allowed. (`030bccd2aae`, #1141; `99ed4310e91`, #1147; `6dc6ca1c6c9`, #1061; `aa68a9c2a55`, #1056; `ebb1c10167e`, #1177)

## Known Issues

- **`--initialize` with `--default_table_encryption=ON` aborts** — Upstream MySQL 8.4.11 (the fix for Bug#39114059) assumes the `mysql` tablespace is unencrypted during initialization. With `--default_table_encryption=ON` that assumption is false, so `mysqld --initialize` aborts with `ERROR 3825 Request to create 'unencrypted' table while using an 'encrypted' tablespace` and leaves the new data directory unusable. A fix is in progress on `dbentley/fix-initialize-encryption`.
